## 1. 目标

将 `traffic-control-plane` 的流量 runner 从“独立动作按权重随机触发”调整为“完整客户购物生命周期优先”。每条流量应模拟一个演示客户完成真实登录、商品探索、随机加购、结算、订单查询，并以成功支付或取消待支付订单收尾。

该能力用于制造可解释、可关联的常规业务流量，以支持订单、库存、支付、履约、通知及混沌场景的观测和验收。常规生命周期只走预期成功或客户取消；支付、库存、促销和下游调用的失败结果由独立故障注入场景制造，不能由常规随机行为混入。

## 2. 范围

### 2.1 包含的主场景

每次生命周期使用同一演示账号、同一请求关联上下文和同一订单归属，按以下顺序执行：

1. 使用预置演示账号真实登录。
2. 随机浏览商品列表、搜索结果或商品详情。
3. 保留该演示客户已有购物车明细，并从可售商品中随机选择 $1 \ldots N$ 个尚未在购物车中的 SKU，以随机数量继续加购。
4. 读取购物车、默认地址和当前客户可用优惠券；没有地址时创建一条受控的演示地址并设为默认地址，再按配置选择“使用优惠券”或“不使用优惠券”场景后创建订单。
5. 查询刚创建的订单，确认其为 `PENDING_PAYMENT`。
6. 按配置选择一个收尾分支：
   - 创建支付意图并成功确认支付；或
   - 仅在订单仍为 `PENDING_PAYMENT` 时取消订单。
7. 再次查询订单，记录支付、取消或后续履约推进后的实际状态。

所有业务请求必须经 `gateway-service`；runner 不得直接访问业务服务。

### 2.2 不包含的内容

- 常规生命周期不模拟失败或未知支付结果；它们属于显式故障注入场景。
- 不将物流查询作为主生命周期的必经步骤。
- 不修改 Shopfront 的消费者体验。
- 不改变混沌注入协议或控制能力。
- 不允许 runner 用本地猜测的订单状态跳过服务端查询。
- 不允许 runner 通过数据库、内部促销 API 或固定券 ID 获取、生成或占用优惠券。

## 3. 用户与权限边界

| 主体 | 能力 | 限制 |
| --- | --- | --- |
| 培训运营人员 | 配置生命周期流量、暂停、恢复、调速并查看非敏感活动 | 仅可通过运营控制台；配置变更须审计 |
| 流量 runner | 使用受控演示客户登录并调用客户 API | 仅经 Gateway；只能使用显式配置的演示账号 |
| 演示客户 | 正常客户 API 访问 | 仅访问自身购物车、地址、订单和支付资源 |

runner 使用真实客户登录，意味着它不再以 `TRAFFIC_RUNNER` 服务凭据代表客户发起主生命周期请求。账号密码只允许由控制面服务端通过环境变量或 Secret 读取；不得出现在页面、客户端 JavaScript、日志、Redis 活动、MySQL 流量记录或错误消息中。

生产或共享环境必须能显式禁用“账号登录流量模式”；启用时必须使用部署注入的 Secret，禁止依赖仓库中的示例密码。

## 4. 业务规则

| 规则 | 要求 |
| --- | --- |
| 账号 | 默认支持 `alice@example.com` 与 `bob@example.com`；可配置更多启用账号。 |
| 会话 | 一条生命周期中的全部受保护请求使用同一客户会话；必要时刷新 token。 |
| 选品 | 常规流量只能从目录 API 返回的可售、库存为正的商品中选择；库存为零、下架或价格异常属于故障注入验证，不作为随机常规结果。 |
| 加购 | 保留已有购物车明细；本次随机新增 SKU 必须互异且不得与现有 SKU 重复，商品种类和单 SKU 数量分别不超过 runner 配置上限。 |
| 地址 | 优先使用默认地址、其次使用首条地址；没有地址时经客户 API 创建一条确定性演示地址并设为默认地址。 |
| 优惠券选择 | 每个生命周期按配置随机选择使用或不使用优惠券。使用时仅从该登录客户的可用券 API 返回项中选择一张；没有合格券时记录 `NOOP/COUPON_UNAVAILABLE` 并无券结算。 |
| 无券结算 | `couponId` 为空或省略时，服务端不得自动选择、预留或消耗任何优惠券。 |
| 有券结算 | checkout 仅提交已选择的 `couponId`；服务端必须重新校验归属、有效期、启用状态、门槛和原子可预留性。 |
| 优惠券补充 | worker 在启动时及之后每 6 小时经 Gateway 触发补券；`promotion-service` 保持券发行、状态转换和幂等规则的唯一所有者，runner 不生成券。失败应在当前窗口内受控重试，成功标记前不能视为本窗口完成。 |
| 库存补充 | worker 按与优惠券相同的启动补齐和六小时周期经 Gateway 触发库存补齐；`inventory-service` 是库存基线、补货计算和原子写入的唯一所有者。常规 runner 不调用 reset。 |
| 结算 | 复用标准 `POST /api/checkout`，使用唯一幂等键；不提交权威金额或商品明细。 |
| 查询 | 订单创建后和收尾后均查询订单；以服务端返回的状态为准。 |
| 支付 | 支付分支仅执行成功确认；不传递 runner 专用的支付结果控制头。 |
| 取消 | 取消前必须重新读取订单；仅允许取消 `PENDING_PAYMENT`。 |
| 待支付订单 | worker 停止、部署中断或未选择收尾操作时，订单允许保留为 `PENDING_PAYMENT`，由原有订单预占到期与补偿机制处理；runner 不把它视为异常或强制 reset。 |
| 归属 | 订单、支付和取消必须使用创建订单的同一客户会话。 |
| 秘密 | 密码、access token、session/refresh token 均不得持久化或展示。 |

## 5. 流量配置与可观测性

生命周期 runner 使用真实演示客户登录，不使用 runner credential。控制台只允许配置
`60s`、`30s`、`20s`、`10s` 四档串行间隔、最大商品种类、单 SKU 数量、成功支付比例和优惠券使用比例。
账号 JSON 仅由服务端环境变量或部署 Secret 注入；账号配置为空或无效、或内部服务密钥缺失时 worker fail-closed。账号参与状态由控制台写入 `runner_customer_whitelist`，不放在环境变量中。
补券和库存补齐由 worker 启动时及 UTC 每六小时经 Gateway 触发，领域服务独占业务数据写入；常规生命周期不调用 inventory reset。

### 5.1 配置

runner 配置至少包含：

- 生命周期模式启用状态。
- 串行生命周期执行间隔，只能选择 `60s`、`30s`、`20s` 或 `10s`。
- 最大商品种类 `maxItems` 与单 SKU 最大数量 `maxItemQuantity`。
- 成功支付比例 `successfulPaymentRatio`，取值范围为 $[0,1]$。
- 取消比例，固定为 $1 - successfulPaymentRatio$。
- 优惠券使用比例 `couponUsageRatio`，取值范围为 $[0,1]$；其余生命周期明确走无券结算。
- 每个演示账号的可用券池及库存基线目标数量和补充阈值；仅允许由服务端维护配置。补券客户集合必须覆盖所有已启用 lifecycle account 的 `expectedCustomerId`。
- 固定补券周期：worker 启动后立即协调一次，此后每 6 小时执行一次；多 worker 实例只允许一个实例执行同一周期。
- 固定库存补齐周期：worker 启动后立即协调一次，此后每 6 小时执行一次；多 worker 实例只允许一个实例执行同一周期。
- 启用的演示账号标签和数量。

生命周期严格串行执行：下一次仅在上一次结束后、再等待所选间隔后启动。控制台不显示或接受 QPS；显示“目标执行间隔”“已完成生命周期数”“上次完成时间”和“实际平均间隔”。现有独立动作流量如需保留，必须作为显式的高级背景流量配置，不能与主场景语义混淆。

### 5.2 活动记录

每条生命周期及其子步骤都应具备可关联记录。运营人员可查看：

- 生命周期 ID、`trafficRunId`、`traceId`、账号标签或客户 ID。
- 子步骤名称、开始/完成时间、耗时、结果、稳定错误码。
- 购物车版本、订单 ID、订单号、支付 ID 和服务端返回的订单状态。
- 选择的 `couponId`、是否请求使用优惠券、实际应用的优惠券 ID、补券/库存补齐结果、窗口 ID、重试次数及稳定错误码。
- 购物车初始明细数、本次新增 SKU/数量、是否自动创建地址、创建的地址 ID、是否留下 `PENDING_PAYMENT` 订单及原因。
- 生命周期结果：完成、失败或无可执行候选的 `NOOP`。

记录不得包含邮箱以外的账号秘密、密码、authorization header、access token、session token 或 refresh token。

## 6. 验收标准

1. runner 能从至少两个启用演示账号中随机选择一个，并经 `POST /api/auth/login` 获得客户会话。
2. 同一生命周期内的购物车、checkout、订单查询、支付或取消请求均携带同一客户 bearer token，且归属该登录客户。
3. runner 在保留已有购物车的前提下，只从目录 API 返回的可售商品中随机加购，且本次随机种类与数量不超过配置边界。
4. 演示客户没有地址时，runner 经 Gateway 创建并选择一条归属正确的默认演示地址；已有地址不会被覆盖。
5. runner 按 `couponUsageRatio` 覆盖使用券和无券结算；无券 checkout 不得创建优惠券预留或改变可用券状态。
6. 使用券的 checkout 只提交当前登录客户通过 Gateway 查询到的可用券；服务端拒绝跨客户、过期、已使用、门槛不符或并发已占用的券。
7. 演示账号的可用券池和商品库存均在启动补齐及六小时周期后幂等恢复基线；取消或 checkout 失败则复用服务端释放的同一券或库存预占，绝不调用 reset。
8. 每条成功创建订单的生命周期都执行创建后查询和收尾后查询；中断产生的 `PENDING_PAYMENT` 订单被允许保留。
9. 支付分支按标准客户 API 创建支付意图并确认成功，未使用 `X-Traffic-Runner-Payment-Strategy`；常规链路出现失败或未知支付时应记录为故障注入结果，不作为随机业务分支。
10. 取消分支仅取消经最新查询确认仍为 `PENDING_PAYMENT` 的订单；已支付或其他状态订单不得取消。
11. 缺少可售商品、可用券、地址创建失败、登录失败、token 过期或订单状态竞争时，runner 记录明确结果，不泄露秘密且不跨客户操作资源。
12. 控制台仅可选择四种串行执行间隔，配置支付、取消和优惠券使用比例，查看生命周期与子步骤关联，并以乐观锁保护配置更新。
13. 单元、类型检查、lint 和构建均通过；端到端验证覆盖两个账号、有券/无券、支付成功、取消、地址创建、库存补齐和待支付订单保留分支。

## 7. 成功指标

| 指标 | 用途 |
| --- | --- |
| 生命周期开始/完成/失败/NOOP/中断数、实际执行间隔 | 串行调度、可用性和数据准备情况 |
| 登录与 token 刷新失败率 | 身份链路健康度 |
| 浏览到加购、加购到 checkout 转化率 | 流量真实性与交易漏斗 |
| checkout 成功率 | 商品、地址、库存与结算链路健康度 |
| 有券/无券结算数、优惠券不可用率 | 优惠券分支覆盖与演示券池健康度 |
| 优惠券预留、确认、释放和补充数 | 优惠券一致性与补券任务健康度 |
| 库存预占、确认、释放和补齐数 | 库存基线与补货任务健康度 |
| 成功支付数与取消数 | 收尾分支分布是否符合配置 |
| 目标与实际支付/取消/有券比例 | 运行策略是否按预期覆盖 |
| 生命周期总耗时及子步骤耗时 | 定位慢服务和故障注入影响 |
| 按 `traceId` 关联的订单状态 | 端到端可观测性和归属正确性 |

实现约束与接口细节见 [technical-design.md](technical-design.md)。
