## 1. 产品定义

故障演练控制面是 `traffic-control-plane` 中面向运营人员的私有工具。它在受控环境内启动、观察和停止与真实业务路径一致的压力、依赖和资源异常，以训练定位、修复和恢复能力。

控制面不是消费者产品的一部分。客户只能经过 `shopfront -> gateway-service` 使用商城；客户界面、客户 BFF 与公开 API 不得暴露运营控制入口、运行详情或内部目标服务地址。

## 2. 目标与边界

### 2.1 目标

1. 任一时刻全环境只允许一条活动演练；每次演练均有明确的目标业务路径、持续时间、运行标识、操作者与数据库运行记录。
2. 除内存耗尽外，所有可恢复场景在到期后自动停止并执行对应恢复动作。
3. 所有场景由真实 SQL、HTTP、Redis、JVM、文件或 MySQL 锁行为产生，不使用 `SLEEP()`、伪造延迟、Controller 直接伪造业务失败或随机假结果。
4. 支持从数据库运行记录中观察业务影响，并将一次操作与其运行记录关联。
5. 慢 SQL 演练必须提供真实、可验证的优化空间：结果语义、SQL 条件、索引和执行计划均可被修复与复测。
6. 预热数据持续保持固定规模的时间窗口，为慢 SQL 演练持续提供当天和历史样本。

### 2.2 非目标

- 不提供向客户公开的混沌、重启、数据治理或服务管理 API。
- 不保留旧的通用多服务 `enable/disable/cleanup` 协议、网络延迟/连接重置面板或兼容 payload。
- 不在业务服务日志、业务服务代码注释、Endpoint 名称或方法名称中使用“故障注入”及同义描述；审计归因保留在受保护的控制面运行记录中。
- 不通过控制面执行任意 shell 命令、Docker 命令、Kubernetes patch、服务名或命名空间。

## 3. 角色与权限

| 角色 | 权限 |
| --- | --- |
| 客户 | 无法访问控制面及其 `/internal/**` 路由。 |
| 培训运营人员 | 查看、创建、停止可恢复运行；查看运行证据；执行获批准的数据清理；在通知服务不可用后申请固定目标重启。 |
| 平台管理员 | 配置演练环境、运行优化迁移、维护重启 broker/RBAC 与容量阈值。 |
| 流量 Runner | 只按受控客户身份经网关访问公开业务 API；不能访问运营控制接口，也不使用 Sam 演练账号。 |

所有变更操作均要求有效运营会话、请求确认/幂等键与审计记录。审计保留操作者、场景、固定目标、参数摘要、关联 ID、时间和结果；不向消费者 API 暴露。

## 4. 运行模型

### 4.1 Fault Run

每次操作建立一条独立运行记录：

| 字段 | 含义 |
| --- | --- |
| `faultRunId` | UUID，控制面、Gateway、目标服务与观测关联使用。 |
| `scenario` | 场景代码。 |
| `target` | 固定的业务操作及所属服务。 |
| `parameters` | 经边界校验后的参数快照。 |
| `startedAt` / `expiresAt` | 启动与到期时间。 |
| `fencingToken` | 单调递增令牌，阻止旧请求或旧控制面实例重新启用资源。 |
| `state` | 生命周期状态。 |
| `stopReason` | 到期、人工停止、调度异常或目标不可用。 |
| `recoveryResult` | 自动恢复或人工恢复的结果。 |

除内存耗尽外，典型状态为：`CREATING -> ACTIVE -> RECOVERING -> RECOVERED`。若已有 `CREATING`、`ACTIVE` 或 `RECOVERING` 运行，创建请求必须被拒绝并返回当前运行；调度/目标异常进入 `FAILED` 并保留错误信息。

内存耗尽运行是例外：到期仅停止新的内存保留动作，已保留对象不会被清理；服务退出或健康检查失败时状态为 `SERVICE_UNAVAILABLE`，只能由运营人员使用固定的通知服务重启操作恢复服务可用性。

### 4.2 持续时间

- 所有场景都必须提供 `durationSec`，由服务端按场景范围校验。
- 控制面在 `expiresAt` 到达时负责停止运行；重启后扫描未终止运行，避免遗留锁、Redis key、请求 worker 或 PSP 行为。
- 每个目标侧操作均携带 `faultRunId`、`expiresAt` 和 `fencingToken`；目标服务拒绝过期或较旧令牌，并在本地到期时自行停止或释放所属资源。控制面的停止请求仅用于加速恢复，不能成为唯一恢复机制。
- 手动停止与到期停止使用同一幂等恢复逻辑。
- 存储容量增长到期后仅停止额外写入，不自动删除已经生成的数据；清理是单独审计操作。

## 5. 场景目录

| 场景 | 固定业务位置 | 真实行为 | 到期后的处理 |
| --- | --- | --- | --- |
| 商品浏览慢 SQL | `catalog-service` 商品浏览当日报表 | 查询名承诺“今日浏览”，但初版遗漏当日范围且缺少匹配索引，聚合历史行为数据。 | 停止控制面的持续报表请求；根因修复另行执行。 |
| 订单查询慢 SQL | `order-service` 客户今日订单报表 | 初版遗漏当日范围、按客户历史记录排序，并对订单明细产生 N+1 访问。 | 停止持续请求；根因修复另行执行。 |
| 商品浏览流量突增 | 网关公开商品浏览 API | 独立并发 worker 按受控并发数持续发起真实浏览请求。 | 取消 worker，正常 Runner 配置不变。 |
| 订单查询流量突增 | 网关公开客户订单查询 API | 独立并发 worker 使用合规演示客户与已记录订单发起真实查询。 | 取消 worker，正常 Runner 配置不变。 |
| Redis 大 key | `catalog-service` 的 `GET /api/products/{sku}` | 控制面在一个运行级商品详情 Hash 中生成 N 个 SKU fields；正常详情 API 和持续读取 worker 通过真实 HTTP、Redis 读取、反序列化与响应链路承受大值压力。 | 停止读取，撤销 active marker，按运行删除 Hash；不影响默认商品缓存和业务数据。 |
| 加购失败 | `cart-service -> catalog-service` 商品校验 | 加购先做真实商品依赖校验；Catalog 暂时不可用时在任何 Cart/CartItem 写入前失败。 | 恢复 Catalog 依赖响应。 |
| 内存耗尽 | `notification-service` 通知保留路径 | 通知数据以高基数方式持续保留，允许 JVM 堆自然耗尽。 | 不自动恢复；健康失败后人工重启通知服务。 |
| 存储容量突增 | `notification-service` 通知持久化路径 | 真实通知持久化事务追加受限、可识别的数据量。 | 停止额外写入；数据保留，人工清理。 |
| 死锁 | `promotion-service` 优惠券预留与过期清理 | 控制面持续调用优惠券预留一致性核对接口；接口在准备好的过期预留上启动两条反向加锁的真实事务。 | 停止持续调用和新竞争事务，放行在途事务。 |
| 表锁 | `inventory-service` 的 `inventories` 表 | 独立连接获取 `LOCK TABLES inventories WRITE`；控制面持续调用库存可用性报表接口，观察真实读请求阻塞。 | 先释放锁和连接，再停止/排空报表调用。 |
| 支付失败 | `payment-service -> psp-simulator` | 支付确认调用独立 HTTP PSP；拒付或超时由真实远程调用产生。 | PSP 恢复正常响应。 |

未指定目标的资源类场景固定为：内存/存储在 `notification-service`，死锁在 `promotion-service`，表锁在 `inventory-service`。这些场景不把 `order-service` 或 `payment-service` 作为目标。

## 6. 慢 SQL 演练与优化闭环

### 6.1 商品浏览报表

`GET /api/products/browse-report` 是商品浏览分析接口，返回 SKU、名称、分类、当前价格、今日浏览次数和最近浏览时间。

初始实现存在两个真实缺陷：

1. 接口语义是“今日浏览”，但查询遗漏日期过滤，统计全部历史 `user_behavior_log`。
2. 行为表没有 `(action_type, target_type, created_at, target_id)` 复合索引。

修复版本必须：

- 使用半开日期范围：`created_at >= CURRENT_DATE AND created_at < CURRENT_DATE + INTERVAL 1 DAY`；
- 添加与访问路径匹配的复合索引；
- 用结果正确性和 `EXPLAIN`/`EXPLAIN ANALYZE` 验证从全历史扫描转为当日范围扫描。

### 6.2 订单查询报表

`GET /api/orders/query-report` 仅查询当前认证客户的今日订单，返回订单状态、金额、创建时间、商品数和总数量。

初始实现存在三个真实缺陷：

1. 缺失当前日期范围，遍历客户全部订单历史；
2. 缺少 `(user_id, created_at, id)` 复合索引；
3. 明细逐订单读取，形成 N+1 查询。

修复版本必须补足日期范围和复合索引，并使用一个投影/分组查询完成订单与明细汇总。报表运行停止不代表已完成优化；只有部署应用修复和对应迁移、并得到正确结果及改善执行计划后，优化状态才可标记为已验证。

## 7. 数据预热产品规则

### 7.1 固定滑动窗口

`product_price_history` 与 `user_behavior_log` 每张表均按东八区自然日分区，并维持：

$$180 \text{ 个自然日} \times 500{,}000 \text{ 条/日} = 90{,}000{,}000 \text{ 条}$$

- 初始建立“今天 + 前 179 个自然日”的 180 个日期桶。
- 每个日期桶 500,000 条数据。
- 每天日期切换后补充当天 500,000 条。
- 新建当天分区并删除窗口外最早分区，维持约 90M 的固定规模。
- 价格历史以 `effective_at` 划分桶；行为日志以 `created_at` 划分桶。
- 每个行为日期桶必须包含足量 `PAGE_VIEW`、`PRODUCT` 与 SKU 目标数据。

### 7.2 可见状态与保护

控制台/状态 API 展示 `BACKFILLING`、`APPENDING`、`ROLLOVER_CLEANUP`、`ERROR` 或 `DISABLED`，并展示总行数、目标行数、当天配额、当天已完成量、写入速率、最早/最新时间、表大小、过期分区删除量和租约拥有者。所有“当天”和日切计算统一使用 `+08:00`。

空间或表大小触发阈值时，预热暂停而不是继续写满磁盘。预热进程重启时从表+日期配额继续；多个 worker 仅允许一个 Redis 租约拥有者写入。

## 8. 控制台体验

控制台使用场景化卡片，不提供旧的泛化服务多选或网络故障面板。

每张卡片展示：

- 固定的业务操作和目标服务；
- 必填持续时间和仅该场景允许的参数；
- 当前状态、开始时间、到期倒计时、运行事件与恢复证据；
- 停止操作及其执行结果；
- 关联的运行 ID、Trace 关联入口和审计结果。

慢 SQL 卡片还展示报表语义、当前数据窗口、基线执行计划证据、修复迁移/应用版本及修复后的验证状态。运行详情仅展示控制面保存在数据库中的事件和恢复结果，不新增指标或业务服务日志。

内存卡片显示保留条目/字节、通知服务健康状态；仅当服务不可用时显示确认式“重启通知服务”操作。该操作没有可编辑的服务名称。

Redis 大 key 卡片显示一个 Hash、N 个 field、每 field 逻辑大小、总逻辑字节、Redis 实际占用摘要、详情读取结果和恢复结果。N 表示 field 数，不是顶层 key 数，也不是读取并发；页面不接受任意 Redis key/value。到期或人工停止时先停止新详情读取，再等待/取消在途请求，撤销 active marker，最后删除运行专属 Hash。详细的商品详情 cache-aside、probe field 和观测规则见 [商品详情缓存专题产品规格](../scenarios/catalog-product-detail-cache/product.md)。

当前控制面实现对创建操作显示确认对话框，详情和历史列表只允许对具体 `faultRunId` 执行 cleanup；不再从页面调用按场景清理商品缓存的旧入口。

死锁卡片显示优惠券预留一致性请求的成功/失败、请求延迟、运行事件和恢复状态；真实 MySQL `1213`、原始 SQLException 堆栈和 JDBC trace 作为数据库排查证据。表锁卡片显示库存可用性报表请求结果、阻塞/超时结果和锁释放状态。两类卡片在运行到期或人工停止时停止各自的持续调用。

## 9. 验收标准

1. 全环境同一时刻只能有一个 `CREATING`、`ACTIVE` 或 `RECOVERING` 运行；每个可恢复运行都有 `faultRunId`、`expiresAt` 与 `fencingToken`，到期后由控制面和目标服务均能停止并记录恢复结果。
2. 每类场景的效果来自真实数据库、HTTP、Redis、JVM 或锁路径；不使用假延迟或假业务结果。
3. 商品和订单慢报表能复现“语义为今日、实现扫描历史”的问题；完成修复后结果只含当日数据，并能观察到执行计划改善。
4. 流量突增停止后不修改或重置正常 Runner 的配置和串行生命周期。
5. 加购依赖失败不写入 Cart、CartItem 或版本；恢复后合法商品可正常加购。
6. Redis 大 key 运行固定使用 Catalog 商品详情 API；一个运行只产生一个 Hash，field 数为 N，每个 value 的逻辑 UTF-8 字节数为 S。停止后撤销 marker、排空详情读取并清理本次运行 Hash，且不影响默认商品缓存或业务数据。
7. 内存场景允许服务不可用，且必须通过受保护的固定目标重启恢复健康；不承诺自动恢复。
8. 预热稳定维持每表约 90M 行、180 天窗口和每日 50 万行配额；按东八区日分区，每日新增和过期分区删除均可观测。
9. 死锁通过持续调用优惠券预留一致性核对接口观察真实 MySQL 死锁；表锁通过持续调用库存可用性报表接口观察真实读阻塞，并在停止后恢复请求完成。
10. 控制面操作受运营权限、确认与审计保护；消费者路径不存在运营控制入口。
11. 运行记录及其事件仅保留 7 天；定期清理不影响正在运行或尚未恢复的记录。
